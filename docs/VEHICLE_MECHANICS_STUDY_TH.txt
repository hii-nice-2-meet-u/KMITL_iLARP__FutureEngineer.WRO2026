1. สรุปสำหรับคนรีบ
======================================================================

ห้าข้อที่มีผลมากที่สุด เรียงตามผลตอบแทนต่อแรงที่ลง

  1) velocity.h (yaw rate) ถูกวัดแล้วทิ้งทุก tick
     แก้ 2 บรรทัด ปลดล็อก 4 อย่าง: deskew LiDAR, วัดมุมล้อจริง,
     วัดความคืบหน้าโค้งจริง, วัดแรง g ด้านข้างจริง

  2) หนึ่งสแกน LiDAR คือการเบลอ 50 ms ที่ถูกติดป้ายว่าเป็นจุดเวลาเดียว
     ที่ 0.45 m/s เท่ากับ 22.5 mm = 56% ของ wall_corner_stability_tolerance_m
     นี่อธิบายอาการยืนยันมุมผนังไม่นิ่งได้ตรง ๆ

  3) แรง g ด้านข้างจริงอยู่แค่ 0.018-0.046 g
     สรุป: การลื่นไถลของยางไม่มีนัยสำคัญ ไม่ต้องสร้าง dynamic model
     ตัวไม่รู้จริงคือแผนที่ pulse -> มุมล้อ ไม่ใช่ยาง

  4) turn_entry_blend_rad = 22.5 deg แต่เซอร์โวต้องการแค่ 4.1-6.7 deg
     ค่านี้ควร derive จาก max_steering_rate_rad_s ไม่ใช่จูนมือแยก

  5) ควรเปลี่ยนภาษากลางจาก delta เป็น kappa
     kappa บวกกันเชิงเส้นได้ delta บวกกันไม่ได้
     แก้ปัญหาการหลบสิ่งกีดขวางเชิงสถาปัตยกรรม (F-05/F-06) และผูก
     ความเร็วกับการเลี้ยวได้ฟรี

2. สัญญาณที่วัดได้แล้วทิ้ง: velocity.h
======================================================================

โค้ดปัจจุบัน (open/main.cpp:153-160, obstacle/main.cpp:160-166)

  sfe_otos_pose2d_t position, velocity, acceleration;
  otos.getPosVelAcc(position, velocity, acceleration);
  const float speed_mps = std::hypot(velocity.x, velocity.y);

sfe_otos_pose2d_t มีสมาชิก .x .y .h ครบทั้งสามตัว
  velocity.x, velocity.y  ความเร็วเชิงเส้นในกรอบโลก
  velocity.h              อัตราการหมุน omega (rad/s)   <-- ถูกทิ้ง
  acceleration            ความเร่งทั้งชุด               <-- ถูกทิ้งทั้งก้อน

ปัญหาของ hypot
  ก) ได้ขนาดอย่างเดียว ไม่มีเครื่องหมาย ถอยหลังกับเดินหน้าแยกไม่ออก
  ข) ทิศทางของเวกเตอร์ความเร็วหายไป ซึ่งคือ sideslip ทั้งหมด
  ค) ถ้ารถหมุนอยู่กับที่ hypot ให้ค่าใกล้ 0 ทั้งที่ omega ไม่ใช่ 0

สิ่งที่ควรคำนวณแทน

  ความเร็วมีเครื่องหมาย
    v = velocity.x * cos(psi) + velocity.y * sin(psi)

  อัตราการหมุน
    omega = velocity.h

  มุมล้อจริงที่วัดได้ (จากจลนศาสตร์ bicycle model กลับด้าน)
    delta_meas = atan(L * omega / v)        เมื่อ |v| > v_min (เช่น 0.05)

delta_meas สำคัญมากเพราะสองเหตุผล
  1) เป็นตัววัดสำหรับ system identification ของแผนที่ pulse -> มุมล้อ
     ซึ่งเป็นสมมติฐานที่โค้ดตั้งไว้แต่ไม่เคยพิสูจน์ (ดูข้อ 8)
  2) เป็น feedback ของพวงมาลัยที่ระบบไม่เคยมี ตอนนี้สั่ง delta แบบ
     open-loop 100% ไม่มีทางรู้ว่าล้อไปถึงมุมที่สั่งจริงหรือไม่

ผลพลอยได้: update_turning() ปัจจุบันจำลอง omega ด้วย
  turn_reference_progress_rad_ += reference_speed_mps / radius_m * dt_s
ทั้งที่เซนเซอร์วัดค่าจริงให้อยู่แล้ว ใช้ค่าวัดจะแม่นกว่าและไม่สะสม error

3. หนึ่งสแกน LiDAR คือการเบลอ 50 ms
======================================================================

โค้ดปัจจุบัน (lidar_module.cpp)

  constexpr sl_u16 TARGET_RPM = 1200;             // 20 Hz -> T = 50 ms
  lidar_driver_->ascendScanData(nodes, count);    // เรียงตามมุม
  processScan(nodes, count);
    -> data.timestamp_us = steady_clock::now();   // เวลา "หลัง" สแกนจบ

จุดที่มุม 0 องศา กับจุดที่มุม 359 องศา ถูกวัดห่างกันได้ถึง 50 ms
แต่ได้ timestamp เดียวกัน แล้ว polar2cartesian ปฏิบัติกับทุกจุดเสมือน
ถูกวัดพร้อมกัน

ขนาดของความคลาดเคลื่อน

  v          เลื่อนตำแหน่ง/สแกน     หมุน/สแกน (ที่ R = 0.45)
  0.28 m/s   14.0 mm               1.78 deg
  0.45 m/s   22.5 mm               2.86 deg

ตัวเลขที่สำคัญที่สุดในเอกสารนี้

  wall_corner_stability_tolerance_m = 0.040 m
  skew ที่ 0.45 m/s                 = 0.0225 m = 56% ของ gate

มุมผนังด้านในอยู่ที่ปลายไกลของ segment คือจุดที่ถูกวัด "เก่าที่สุด"
เทียบกับ pose ที่ใช้แปลงมันเข้าพิกัดโลก ดังนั้นความไม่นิ่งของ
wall_corner ไม่ได้มาจาก noise ของ LiDAR อย่างเดียว แต่มาจากการที่
เราเทียบจุดที่วัดตอน t-40ms กับ pose ตอน t

และจะแย่ลงอีกหลัง T-03 เพราะ corner_radius_m = 0.45 ทำให้จุด trigger
ขยับออกไป ~0.50 m ผนังไกลขึ้น = จุดปลาย segment ยิ่งถูกวัดเก่าลง

ผลกระทบอีกจุดที่มองข้ามง่าย
  calculate_center_cross_track_error() = 0.5 * (inner - outer)
  สมมติว่าผนังซ้ายกับขวาถูกวัดพร้อมกัน แต่จริง ๆ ห่างกัน ~25 ms
  ตอนเลี้ยว กึ่งกลางช่องที่คำนวณได้จึงมี bias ที่เปลี่ยนเครื่องหมาย
  ตามทิศการเลี้ยว (CW/CCW ได้ bias คนละทาง)

วิธีแก้: deskew ต่อจุด

  ขั้น 1 หาเวลาต่อจุด
    t_i = t_end - (1 - phi_i) * T          phi_i = สัดส่วนรอบที่สแกนไปแล้ว

    ข้อควรระวัง: ascendScanData เรียงจุดตามมุม ซึ่งทำลายลำดับเวลา
    ต้องคำนวณ t_i ก่อนเรียก ascendScanData หรือเก็บมุมเริ่มสแกนไว้

  ขั้น 2 แปลงทุกจุดเข้ากรอบเวลาเดียวกัน (t_end)
    dt_i = t_end - t_i
    p_corr = R(-omega * dt_i) * p_raw - v * dt_i * yhat

    โมเดล constant-velocity เพียงพอสำหรับหน้าต่าง 50 ms
    งานวิจัยใช้โมเดลลำดับสูงกว่า (constant jerk) เฉพาะกับการเคลื่อนที่
    ที่รุนแรงกว่านี้มาก

หมายเหตุ: นี่คือสิ่งเดียวกับที่ระบบ LiDAR-Inertial Odometry ทำด้วย IMU
แต่ของเราดีกว่าตรงที่ OTOS ให้ทั้ง v และ omega โดยตรง ไม่ต้อง integrate
IMU (ซึ่งมี drift)

5. การหาเส้น: TLS ถูกต้อง แต่ไม่มี robust estimator
======================================================================

fit_line_segment() ใช้ total least squares ผ่าน eigenvector ของ
scatter matrix

  theta = 0.5 * atan2(2*Sxy, Sxx - Syy)

เรื่องนี้ถูกต้องแล้ว และเป็นข้อดีของโค้ดชุดนี้
  ordinary least squares จะผิด เพราะสมมติว่า error อยู่แกน y อย่างเดียว
  แต่ LiDAR มี error ทุกทิศ TLS ลด error ตั้งฉากกับเส้น ซึ่งถูกต้อง
  ทางฟิสิกส์

ที่ขาด: ไม่มีการตัด outlier เลย

  มีแค่ gate  if (rms_error_m > max_line_error_m) ทิ้งทั้ง segment
  ผลคือจุดสะท้อนผิดจุดเดียว (specular reflection, ขอบโต๊ะ, ขาเก้าอี้)
  ทำให้เสียผนังทั้งเส้นในเฟรมนั้น

ข้อสังเกตที่เชื่อมกับ finding เดิม
  อาการ "ผนังกะพริบ" คือสิ่งที่ F-14 ไปเจอที่ปลายทาง
  (stanley_.reset() ถูกเรียกทุกเฟรมที่ผนังหาย ทำให้ integral ถูกล้างซ้ำ ๆ)
  แต่ต้นเหตุน่าจะอยู่ตรงนี้ การแก้ที่ต้นทางดีกว่าแก้ที่ปลายทาง

วิธีแก้ที่เบาที่สุด: fit สองรอบ
  1) fit ปกติ
  2) ทิ้งจุดที่ระยะตั้งฉาก > 2.5 * rms
  3) fit ใหม่จากจุดที่เหลือ
วิธีมาตรฐานกว่า: IRLS ด้วย Huber weight

หมายเหตุเรื่องการถ่วงน้ำหนัก
  ทุกจุดถ่วงน้ำหนักเท่ากัน ในทางทฤษฎี noise ของระยะจะฉายลงบนแนวตั้งฉาก
  กับผนังเป็นสัดส่วน cos(มุมตกกระทบ) จุดที่ยิงเฉียดมาก ๆ จึงให้ข้อมูล
  ระยะตั้งฉากที่ดีแต่ให้ข้อมูลมุมที่แย่ ประเด็นนี้เป็นเรื่องรอง
  เทียบกับการไม่มี outlier rejection

6. เกณฑ์ตัด segment เป็นค่าคงที่ ทั้งที่ข้อมูลไม่คงที่
======================================================================

max_point_gap_m = 0.12 (ค่าคงที่)

แต่ระยะห่างระหว่างจุดข้างเคียงโตเชิงเส้นตามระยะ  ds = r * dphi

  ที่ dphi = 0.225 deg (S3 ~32 kHz, 20 Hz)

  ระยะ r    ช่องว่างธรรมชาติ    เกณฑ์ที่ใช้     อัตราส่วน
  0.3 m     1.2 mm             120 mm          100x
  1.0 m     3.9 mm             120 mm           31x
  3.0 m     11.8 mm            120 mm           10x

เกณฑ์เดียวจึงหลวมเกินไปทุกระยะ และหลวมมากที่ระยะใกล้
ผลคือมันจะ "เชื่อม" ผนังสองด้านที่มีช่องว่างจริงเข้าเป็นเส้นเดียว
ซึ่งเป็นปัญหาตรงกับที่ต้องตรวจจับมุมผนัง

คำตอบมาตรฐานในงานวิจัย: adaptive breakpoint detector (Borges & Aldon)

  D_max = r_{i-1} * sin(dphi) / sin(lambda - dphi) + 3 * sigma_r

  lambda   มุมตกกระทบเลวร้ายสุดที่ยอมรับ (พารามิเตอร์ออกแบบ ~10 deg)
  sigma_r  ค่าเบี่ยงเบนมาตรฐานของการวัดระยะ

เกณฑ์นี้โตตามระยะและตามความเฉียงของผนังโดยอัตโนมัติ

7. พลศาสตร์ที่ไม่มี และข่าวดีคือไม่ต้องมี
======================================================================

คำนวณแรงด้านข้างจริงที่ความเร็วใช้งาน (R = 0.45 m หลัง T-03)

  a_lat = v^2 / R

  v          a_lat          เป็น g
  0.28 m/s   0.174 m/s2     0.018 g
  0.45 m/s   0.450 m/s2     0.046 g

ขีดยึดเกาะของยางบนพื้นเรียบทั่วไปอยู่ราว 1 g
เราใช้อยู่ 1/20 ของนั้น

ข้อสรุปที่มีค่า
  การลื่นไถลของยาง (slip angle, tyre model, load transfer) ไม่มี
  นัยสำคัญเลยในระบบนี้
  -> kinematic bicycle model เพียงพอ 100%
  -> ไม่ต้องเสียเวลาสร้าง dynamic model
  -> ตัวไม่รู้จริง ๆ คือแผนที่ pulse -> มุมล้อ ของ linkage ไม่ใช่ยาง

ผลต่อ max_lateral_acceleration_mps2 = 0.50
  ค่านี้เป็นค่าเดา และหลัง T-03 มันไม่ใช่ตัวจำกัดอีกแล้ว
  (turning_speed_mps = 0.28 เป็นตัวจำกัดแทน)
  ค่าจริงวัดได้จาก a_lat = v * omega เมื่อเริ่ม log velocity.h

8. การเบลนด์ขาเข้าโค้ง: อนุรักษ์นิยมเกินจริง 3-5 เท่า
======================================================================

turn_entry_blend_rad = 22.5 deg ถูกจูนด้วยมือ ไม่ได้อิงความสามารถ
จริงของเซอร์โว ลองคำนวณย้อนจากสเปก

  เซอร์โวไปถึง delta = 20 deg ที่ max_steering_rate_rad_s = 3.0 rad/s
    t = 20 * PI/180 / 3.0 = 0.116 s

  ระยะที่วิ่งได้ใน 116 ms และมุมส่วนโค้งเทียบเท่า (R = 0.45)
    v = 0.28 -> 33 mm -> 4.1 deg
    v = 0.45 -> 52 mm -> 6.7 deg

  ฮาร์ดแวร์ต้องการ 4-7 deg แต่คอนฟิกให้ 22.5 deg

ค่านี้ควรถูก derive ไม่ใช่จูน
  s_ramp = v * (delta_max / steering_rate)

ปัญหาเชิงรูปแบบอีกข้อ

  feedforward_rad = ... * min(entry_weight, exit_weight)

  min() ของสองฟังก์ชันทำให้เกิดจุดหักของอนุพันธ์ตรงที่สองเส้นตัดกัน
  โปรไฟล์ความโค้งจึงไม่ C1 ที่จุดนั้น

รูปแบบที่ถูกต้องตามหลัก: clothoid (Euler spiral)
  ความโค้งเป็นเชิงเส้นกับระยะทางโค้ง  kappa(s) = kappa_max * s / s_ramp
  งานวิจัยระบุว่าเป็นมาตรฐานสำหรับรถ Ackermann เพราะรถเปลี่ยนมุมเลี้ยว
  ทันทีไม่ได้ และเส้นทางต่อเนื่องทั้งตำแหน่ง heading และความโค้ง

การกรองซ้อนกัน 4 ชั้นที่มีอยู่ตอนนี้
  1) smoothstep blend ของ feed-forward
  2) low-pass tau = 0.035 s
  3) slew limit 3.0 rad/s
  4) servo step limit 500 us/tick
แต่ละชั้นเพิ่ม phase lag และไม่มีใครรู้ว่ารวมแล้วเท่าไร
ถ้าใช้ clothoid ชั้น 1 หายไปเพราะโปรไฟล์จัดการการไต่ระดับให้แล้ว

9. ความเร็วกับการเลี้ยวไม่ผูกกันในโหมด NORMAL
======================================================================

calculate_corner_speed_mps() ใช้ corner_radius_m ซึ่งเป็นค่าคอนฟิก
ไม่ใช่ความโค้งที่กำลังสั่งจริง

ผลคือใน NORMAL mode ถ้า Stanley สั่งเลี้ยวแรงเพื่อแก้ตำแหน่ง
ไม่มีการลดความเร็วเลย ทั้งที่ฟิสิกส์บอกว่าผูกกันผ่าน

  a_lat = v^2 * tan(delta) / L = v^2 * kappa

สิ่งที่ควรมี

  v_curve = sqrt(a_lat_max / |kappa_cmd|)
  v_target = min(v_mode, v_curve, v_approach)

ใช้ได้ทุกโหมด ไม่ใช่แค่ TURNING และเป็นการลดความเร็วที่ "ถูกต้อง

10. Stanley: ข้อจำกัดที่ตรงกับอาการของงานนี้
======================================================================

งานวิจัยระบุจุดอ่อนของ Stanley สองข้อที่ตรงกับสถานการณ์นี้

  ก) มองแต่ error ปัจจุบัน ไม่มองเส้นทางข้างหน้า จึงแกว่งบนทางโค้ง
     -> นี่คือเหตุผลที่ต้องมีโหมด TURNING แยกออกมาทั้งโหมด
     -> ตัว Stanley เองไม่ได้ออกแบบมาให้เลี้ยวโค้ง 90 องศา

  ข) จูนที่ความเร็วหนึ่งแล้วเอาไปใช้อีกความเร็วหนึ่งไม่ได้
     ก้าวร้าวเกินที่ความเร็วต่ำ เฉื่อยเกินที่ความเร็วสูง
     -> เป็นปัญหาตรง ๆ เมื่อ replay speed factor ทำให้ความเร็ว
        เปลี่ยนตามรอบ

softening_speed_mps = 0.20 ในเทอม atan2(k * e_ct, v + v_soft)
คือตัวชดเชยข้อ ข) แต่มันหยาบ

  ที่ v = 0.28  ตัวส่วน = 0.48   v_soft มีน้ำหนัก 42%
  ที่ v = 0.45  ตัวส่วน = 0.65   v_soft มีน้ำหนัก 31%

เกนที่มีผลจริงจึงยังเปลี่ยนตามความเร็วราว 35% ระหว่างสองค่านี้

ทางเลือกที่งานวิจัยเสนอ: hybrid Stanley + pure pursuit
  pure pursuit เสถียรกว่าบนโค้งและทนต่อความไม่ต่อเนื่องของเส้นทาง
  แต่ใช้แค่ cross-track error
  Stanley ใช้ทั้ง heading และ cross-track error
  ระบบ hybrid เลือกใช้ตามสถานการณ์
  -> โครงสร้าง NORMAL/TURNING ที่มีอยู่แล้วก็คือ hybrid แบบหนึ่ง
     เพียงแต่ทำด้วย state machine แทนการ blend

11. ชุดสมการเต็ม เรียงตามชั้น
======================================================================

ชั้น 0 -- เซนเซอร์ -> เรขาคณิต (ชั้นที่ขาดมากที่สุด)

  0a  เวลาต่อจุด
        t_i = t_end - (1 - phi_i) * T
        ** ต้องเก็บก่อน ascendScanData เพราะมันเรียงทับลำดับเวลา **

  0b  deskew
        dt_i = t_end - t_i
        p_corr = R(-omega * dt_i) * p_raw - v * dt_i * yhat

  0c  polar -> cartesian
        x = r * sin(phi)
        y = r * cos(phi)
        ** เครื่องหมายรอผล docs/audit/HARDWARE_CHECKS.md ข้อ 1 **

  0d  breakpoint (adaptive)
        D_max = r * sin(dphi) / sin(lambda - dphi) + 3 * sigma_r

  0e  line fit
        TLS + Huber weighting

  0f  จำแนกผนัง
        ไม่ต้องใช้ wall_correction_rad อีก เพราะ 0b แก้ที่ต้นเหตุแล้ว

  บทบาท: ชั้นนี้คือ measurement model เป็นทั้งอินพุตของ controller
  และเป็นสิ่งที่ simulator ต้องจำลอง ทำถูกครั้งเดียวได้ประโยชน์สองต่อ


ชั้น 1 -- สถานะ

  1a  pose               (x, y, psi) จาก OTOS
  1b  ความเร็วมีเครื่องหมาย  v = velocity.x*cos(psi) + velocity.y*sin(psi)
  1c  อัตราการหมุน         omega = velocity.h
  1d  มุมล้อจริง (วัด)      delta_meas = atan(L * omega / v)


ชั้น 2 -- จลนศาสตร์ (สะพานเชื่อมชั้น 1 กับชั้น 4)

  psi_dot = v * kappa = v * tan(delta) / L
  x_dot   = v * cos(psi)
  y_dot   = v * sin(psi)

  ไม่มีในโค้ดเลย มีแค่รูปกลับด้านซ่อนใน atan2(L, R)
  นี่คือหัวใจของ simulator และเพราะข้อ 7 โมเดลนี้แม่นพอโดยไม่ต้อง
  เติมพลศาสตร์อะไรอีก


ชั้น 3 -- เส้นทางอ้างอิง

  ทางตรง   kappa_ref = 0
  โค้ง     โปรไฟล์ clothoid - arc - clothoid
           kappa(s) = kappa_max * s / s_ramp        (ช่วงไต่ระดับ)
           s_ramp   = v * (delta_max / steering_rate)

  ที่ค่าปัจจุบัน s_ramp = 33-52 mm ไม่ใช่ 22.5 deg (เทียบเท่า ~177 mm)


ชั้น 4 -- ควบคุม (ทุกตัวคืนค่าเป็น kappa)

  ทางตรง   kappa_cmd = tan(delta_stanley) / L
  โค้ง     kappa_cmd = kappa_ref(s) + Kp*e_track + Ki*integral(e_track)
  หลบเสา   kappa_cmd += kappa_avoid ,  |kappa_avoid| <= kappa_avoid_max
  รวม     kappa_cmd = clamp(kappa_cmd, +-tan(delta_max)/L)

  สังเกต: ในโหมดโค้ง feed-forward คือ kappa_ref เอง
  ไม่ต้องมี atan2(L,R) แล้วคูณน้ำหนักเบลนด์อีกต่อไป
  ตัวแปรที่หายไป: turn_entry_blend_rad, turn_exit_blend_rad,
                  turn_entry_steering_rad_


ชั้น 5 -- ความเร็ว (ผูกกับชั้น 4)

  v_curve  = sqrt(a_lat_max / |kappa_cmd|)
  v_target = min(v_mode, v_curve, v_approach)
  v_cmd[k] = v_cmd[k-1] + clamp(v_target - v_cmd[k-1], +-a_max*dt)


ชั้น 6 -- การขับเคลื่อน

  delta_cmd = atan(L * kappa_cmd)              แปลงครั้งเดียว ที่เดียว

  rate limit ชั้นเดียว (แทน 4 ชั้นเดิม)
    |kappa_cmd[k] - kappa_cmd[k-1]| <= kappa_dot_max * dt
    โดย kappa_dot_max derive จาก steering_rate ของเซอร์โว

  pulse = f(delta_cmd)      f จาก system ID ไม่ใช่เชิงเส้น (ดูข้อ 8)
  rpm   = v_cmd * 60 / (PI * wheel_diameter_m)

12. ทำไม kappa ควรเป็นภาษากลาง
======================================================================

ตอนนี้ทุกชั้นพูดภาษา delta (มุมพวงมาลัย)
ข้อเสนอคือให้พูดภาษา kappa (ความโค้ง) แล้วแปลงเป็น delta ครั้งเดียว
ที่ชั้นล่างสุด

เหตุผลสี่ข้อ ทุกข้อแก้ปัญหาที่มีอยู่จริง

  1) kappa บวกกันเชิงเส้นได้ delta บวกกันไม่ได้
     ตอนนี้ update_turning() ทำ
       steering = entry_steering + feedforward + tracking_pid
     การบวกมุมพวงมาลัยแบบนี้ผิดหลักคณิตศาสตร์ เพราะ delta = atan(L*kappa)
     ไม่เป็นเชิงเส้น มันใช้งานได้เพราะมุมเล็ก (tan x ~ x) แต่ error
     จะโตขึ้นเมื่อมุมใหญ่ขึ้น
     ที่ 20 deg: tan(20 deg) = 0.364 เทียบกับ 0.349 rad -> ต่าง 4.3%

  2) ความเร็วผูกกับ kappa ได้ตรง ๆ
     v_max = sqrt(a_lat_max / |kappa|)
     แก้ปัญหาข้อ 9 ได้ทุกโหมด ไม่ใช่แค่ TURNING

  3) การหลบสิ่งกีดขวางกลายเป็นการบวก offset
     kappa = kappa_wall_follow + kappa_avoid
     ** แก้ F-05/F-06 ด้วยสถาปัตยกรรม ไม่ใช่ patch **
     ไม่ต้องเถียงว่า "แทนที่ steering หรือผสม" อีกต่อไป
     และใช้ได้แม้ในโหมด TURNING เพราะเป็นการบวกบนความโค้งของโค้ง

  4) ข้อจำกัดฮาร์ดแวร์แสดงเป็น rate limit ของ kappa ตัวเดียว
     ยุบการกรอง 4 ชั้นในข้อ 8 เหลือชั้นเดียวที่ derive จากสเปกเซอร์โว

ความลื่นไหลที่ได้ไม่ได้มาจากการกรองเยอะขึ้น แต่มาจากการที่ข้อจำกัด
ถูกบังคับที่ชั้นที่มันเป็นเจ้าของจริง

  ปัจจุบัน: ความเร็วเปลี่ยน -> a_lat เปลี่ยนโดยไม่มีใครรู้ ->
            พวงมาลัยไปแก้ทีหลัง -> ต้องกรองเยอะเพื่อไม่ให้กระตุก
  ที่เสนอ:  v_max มาจาก kappa โดยตรง -> ทั้งสองเปลี่ยนพร้อมกันและ
            สอดคล้องกันตลอด -> ต้องการการกรองน้อยลง

13.5  ไม่มี feedback ของพวงมาลัยเลย

      แต่ delta_meas = atan(L * omega / v) วัดได้ฟรีจาก OTOS
      ปิดลูปได้ทันทีถ้าต้องการ

13.6  ascendScanData ทำลายข้อมูลที่ต้องใช้

13.7  acceleration ถูกอ่านแล้วทิ้งทั้งก้อน

ภาคผนวก ก: ตัวเลขและวิธีคำนวณ
======================================================================

ค่าคงที่ที่ใช้
  L = 0.16375 m          wheelbase
  R = 0.45 m             corner_radius_m หลัง T-03
  T = 0.050 s            คาบสแกน ที่ 1200 RPM
  a_lat_max = 0.50       max_lateral_acceleration_mps2 (ค่าเดา)
  steering_rate = 3.0    max_steering_rate_rad_s
  delta_clamp = 38 deg   stanley.max_steering_rad

skew ของสแกน
  translation = v * T
    0.28 -> 0.0140 m
    0.45 -> 0.0225 m
  rotation = (v/R) * T
    0.28 -> 0.62 rad/s * 0.050 = 0.031 rad = 1.78 deg
    0.45 -> 1.00 rad/s * 0.050 = 0.050 rad = 2.86 deg
  เทียบ wall_corner_stability_tolerance_m = 0.040
    0.0225 / 0.040 = 56%

แรงด้านข้าง
  a_lat = v^2 / R
    0.28 -> 0.0784 / 0.45 = 0.174 m/s2 = 0.0178 g
    0.45 -> 0.2025 / 0.45 = 0.450 m/s2 = 0.0459 g

entry blend ที่ฮาร์ดแวร์ต้องการ
  delta_ff = atan2(L, R) = atan2(0.16375, 0.45) = 0.349 rad = 20.0 deg
  t_ramp   = 0.349 / 3.0 = 0.116 s
  s_ramp   = v * t_ramp
    0.28 -> 0.033 m -> มุมส่วนโค้ง 0.033/0.45 = 0.072 rad = 4.1 deg
    0.45 -> 0.052 m -> มุมส่วนโค้ง 0.052/0.45 = 0.116 rad = 6.7 deg

รัศมีวงเลี้ยวต่ำสุดของรถ
  R_min = L / tan(delta_max)
    ที่ 38 deg -> 0.16375 / 0.7813 = 0.210 m
    ที่ 45 deg -> 0.16375 / 1.0000 = 0.164 m

การสุ่มตัวอย่างเชิงมุมของ LiDAR
  จำนวนจุดต่อรอบ = sample_rate * T
    32000 Hz -> 1600 จุด -> 0.225 deg
    16000 Hz -> 800 จุด  -> 0.450 deg
  ระยะห่างจุดข้างเคียง ds = r * dphi   (ที่ 0.225 deg = 0.00393 rad)
    r = 0.3 -> 1.2 mm
    r = 1.0 -> 3.9 mm
    r = 3.0 -> 11.8 mm

ความไม่เป็นเชิงเส้นของ atan ที่ 20 deg
  tan(20 deg) = 0.36397
  20 deg ในหน่วย rad = 0.34907
  ต่างกัน 4.3%
